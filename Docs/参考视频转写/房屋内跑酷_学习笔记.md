# 房屋内跑酷 DEMO —— 学习笔记与设计约束

## 目标

**以蜘蛛侠视角，在《进击的巨人》式的人类住宅内部跑酷。**

参考三个白盒设计视频 + 大量技术资料调研。

---

## ★ 最关键的发现：层高与球的尺度冲突

### 日本住宅的真实层高（有法定效力）

| 数值 | 性质 | 来源 |
|---|---|---|
| **2,100 mm** | **法定最低值**（《建筑基准法施行令》第21条）| 国土交通省官方 PDF |
| 2,400 mm | 当代业界标准 | Housing Japan |
| **2,200 mm** | 昭和町屋风格（**巨人题材应该用这个**）| Housing Japan |

### 日式住宅的空间模块

| 尺寸 | 含义 |
|---|---|
| **910 mm** | 战后「尺贯法」的标准模块 —— 墙/地板/建具都按它统一 |
| 1 间（ken）= 1,818 mm | 一间房的标准宽度 |
| 畳 = 910 × 1,820 mm | 榻榻米 |
| 1 坪 ≈ 3.306 m² | — |

东京都市圈住宅**平均建筑面积 65.9 m²**（日本统计局）。

### 冲突

若取 1 格 = 1 米：

```
层高 2.4 米  vs  球直径 9 格  →  ★ 球根本进不去房间
```

要让球进房间，球半径需 **< 0.6~0.85 格**（当前 4.5）。

若坚持球半径 4.5 格，层高需要 **~9 米** —— 但那就不是日式住宅了。

### 这是设计抉择，不是调参问题

| 选项 | 说明 | 代价 |
|---|---|---|
| **A** | 球做小（半径 1.2~1.5），层高 2.4 | 球很小，摄像机要重调|
| **B** | 球保持 4.5，层高放大到 12~15 | 不再是「日式住宅」 |
| **C** | 不进房间，只做房屋之间的街道跑酷 | 巨人压迫感成立，但少了室内感 |

## ★ 第二重要：室内跑酷这个品类是**空白**

调研的**重要负面结论**：

>所有成熟跑酷游戏（Dying Light、Mirror's Edge、AC、Titanfall/Apex）
> 的室内空间都只是大世界里的一个子区域，**没有一部以室内/房屋为主场景**。

**这意味着无法照抄** —— 必须自己设计。可参考的最接近样本：

### Dying Light《The Tower》（公寓楼内部）

- 一堆小公寓，**楼梯被居民故意炸毁**以阻挡感染者
- → **强制玩家只能靠跑酷上楼**，这是垂直交通的唯一性
- 18 层爆发疫情后被封死，玩家房间在 19 层
- 塔顶有菜园，用通风管道/金属洗衣篮做种植容器

**借鉴点：用一个「物理上不可能走楼梯」的理由，强制跑酷成为唯一通路。**

### Dying Light 的技术教训（Wikipedia，有开发者姓名）

> 最初 Techland 仿Mirror's Edge 的「钩子系统」——设计师在特定位置放钩子。
> **失败原因**：「钩子限制了玩家的自由，因为开发者把钩子放在非常具体的位置。
> 此外，当一个设计师移动了一个钩子的位置，他还必须调整其他钩子的位置，
> 这是一个非常麻烦的过程。」

2012 年 Bartosz Kulon 实现了 **Natural Movement**（自动扫描可攀爬物），
结果引入新问题：
>「由于玩家现在可以从多个方向接近目标……角色经常穿过结构穿模。
> **一些测试者出现了眩晕（motion sickness）。**」

★ **室内三层住宅里「手动摆钩点」几乎必然崩掉**（房间太小、玩家从各种角度到达、穿模）。

### Dying Light 2 的环境-跑酷协同（最有实操价值）

首席环境概念师 Kasia Zielińska 访谈：

> 「游戏里你看到的每一栋建筑都是与关卡设计团队合作创作的，
> 以确保在屋顶上攀爬和奔跑是有趣且令人满意的。
> 对概念美术团队来说 designing buildings that not only follow the art direction
> but also **stick to very strict dimensions that comes with parkour** 是一场巨大的挑战。」

> 「我们从**灰盒阶段**就 literally 参与他们的创作流程。
> 设计建筑时，他们会给我们设定了固定尺寸的原型，
> 我们需要为它们找到视觉方案。**这些原型在我们拿到手之前就已经过玩法测试。**」

★ **官方就是这么做的：关卡先出灰盒原型 → 玩法测试 → 美术配合。**

### Assassin's Creed Unity —— 改造历史建筑的教科书案例

Ubisoft × SIGGRAPH 访谈：

> 「从**玩法**角度看，我们不得不稍微改动内部结构，
> 以**增加几层导航层**。光是重现纪念碑是不够的。
> 人们需要能在里面玩得开心。……我们在巴黎圣母院第二层加了
> **缆绳和香炉**之类的东西，这样玩家在地面以上移动会更容易。」

### ★ AC Unity 的失败教训（对本项目最直接相关）

Eurogamer 评测：

> 「攀爬建筑外部比以往任何时候都更快更顺——
> **但一旦你开始水平移动，在低矮围墙和门框之间快速前进就非常危险**。
> 自由奔跑试图判断你想去哪里……但由于 Unity 密实的环境与它对抗，
> 感觉就像一个**过度热情的字正 autocorrect**。」

Mirror's Edge 的室内则刻意做成线性、单向、被强光收束的隧道
（PCGamer：「inside 全是通向过曝消失点的生硬走廊」）。

★ **历史上所有成熟的跑酷游戏，其设计者都在与
「水平移动时室内障碍物密集」作斗争。**
Mirror's Edge 靠**第一人称**完全回避（Catalyst 设计总监：
「我们想要玩家通过 Faith 的眼睛看游戏，一旦变成第三人称
你就只是在看 Faith」）。

★ **我们做第三人称，就必须正面解决它。**

## 技术实现要点

### 摆荡物理：用位置约束，不用 SpringJoint

**最权威来源**：Spider-Man2 (2004) 技术总监 Jamie Fristrom 的伪代码文章

```csharp
// 1. 记录初始绳长
InitialRopeLength = (PlayerBody.position - GrappleHitPosition).magnitude;

// 2. 每帧：预测下一步位置
Vector3 TestGrapplePosition = PlayerBody.position + PlayerBody.velocity * Time.deltaTime;

// 3. 约束回绳长半径的球面上
Vector3 Test = GrappleHitPosition
             + ((TestGrapplePosition - GrappleHitPosition).normalized * InitialRopeLength);

// 4. 用约束后的位置修正速度
PlayerBody.velocity += (Test - PlayerBody.position).normalized;

// 5. 直接修正位置
PlayerBody.position = Test;
```

Fristrom 区分了 **canned movement（预制动画）** 与
**physical simulation（物理模拟）**，明确选后者。

★ **历史教训**：他早期是在建筑转角**手动摆摆荡点**的，
玩家常「意外粘在两摆点之间的墙上」，手感很差。
解法是 raycast 动态检测 —— 但受当时主机性能限制。

### Unity SpringJoint 的陷阱

- SpringJoint **不强制物体处于指定距离**，而是「试图把它推过去」
  → 玩家有速度后会永远绕着抓点打转，像摆荡但手感不对
- 解法：保留 SpringJoint 但自己接管速度写入
- 或用 ConfigurableJoint 的 linearLimit

### SphereCast 优于 Trigger 抓取

Unity 实践报告：Trigger Collider 在高速移动中会**频繁丢失事件**
（帧间位移过大导致 Collider 来不及重叠）。
改用 SphereCast（连续检测）后失败率 **37% → 1.2%**。
参数：`grabDistance = 1.5f`, `grabRadius = 0.3m`。
⚠️ 中文技术博客，非官方文档，但数据具体可复现。

### 绳长下限 clamp

`Mathf.Clamp(_currentDistance, 0.3f, _grappleDistance)` —— 0.3m 实测下限。
★ **室内 2.4m 层高下，绳长 clamp 下限会成为手感关键参数。**

### 室内摆荡的物理限制（本项目整理）

⚠️ 声明：**没找到任何开发者文章专门讨论「室内摆荡」**。
以下是从上述一手资料提取的、与本场景直接相关的限制：

| 限制 | 依据 | 对策 |
|---|---|---|
| 层高 2.2~2.4m 限制摆荡弧线 | 国交省法定值 | 做**短绳 + 快速摆荡 + 层间折线位移**（每层一次摆荡，而非一荡三层）|
| 天花板是硬性上限，raycast 会大量命中无效抓点 | Dying Light 因此推翻系统 | 对抓点做**有效性验证** |
| 障子/拉门是纸框，一撞就破 | 可整面拆下 | 做成**可破坏物**，破坏后成为新路径 —— 很好的垂直层次机制 |
| 弹簧关节会「绕点打转」| Unity SpringJoint 行为 | 用位置约束法 |
| 绳长下限与收绳速度 | Clamp 0.3m | 室内需要更短最小绳长 + 更快收绳|

### 相机在室内（Unity 官方论坛）

官方推荐 SphereCast，**球半径应接近相机近裁剪面**：

```csharp
var desiredCameraPos = target.position + dollyDir * maxDistance;
var targetDirection = (target.position - camera.position).normalized;
if (Physics.SphereCast(desiredCameraPos, 0.5f, targetDirection,
                      out hit, maxDistance))
{
    distance = Mathf.Clamp(hit.distance, minDistance, maxDistance);
}
```

★ **官方论坛有人提问室内解法但andyz 没有回应**：
> 「能不能在相机和角色之间放一个圆锥或圆柱来扩大控制区域，
> 以避免即使只是部分遮挡（比如穿过门时门框边缘切掉了相机看到的画面）？
> 或者更好的做法，不是把相机向前推，
> 而是**让相机绕着角色移动以避开障碍物**？」

★ **第二个方案（绕行）对室内 DEMO 关键**——
在 4.5~10 畳的房间里，「推近」意味着相机几乎贴到脸上，视角会疯狂抖动。
**但「绕行」只有提问没有答案，需自己做原型。**

### 晕动症（室内摆荡的隐性风险）

Mirror's Edge 高级制作人 Owen O'Brien：

> 「当早期测试者开始在细节丰富的环境中高速移动时，问题就出现了——
> **导致用户在屏幕上的感知与身体的预期不匹配**。」
> 「我们发现，当你在世界中快速移动时，你很快就会晕动病发作。」

★ 注意诊断：**症状不是「移动太快」，而是「视觉运动与身体预期的失配」**。
室内会成倍严重——空间小、参照物变化剧烈、天花板反复掠过。

### 无自然光室内的导航（Dying Light 2 的做法）

> 「在设计资产和室内时，我们知道不会有任何自然光。
> **最大的挑战是确保玩家仅凭手电筒就能理解这个空间。**
> 我们还决定使用**小光点来帮助导航**。」

## 灰盒方法论

### Unity 官方的定义与陷阱

Unity 官方对 greyboxing 的定义：
> 「用简单的形状搭出关卡，
> 以在创建最终美术资产之前**验证关卡设计是否支撑玩法**。」

★ **Unity Academy 有门课专门讲灰盒的室内问题**
（`Greybox Prototypes with ProBuilder`）：

> **「Topic 2: Flipping Face Normals for Interior Rooms」**
> - 解释为什么一个形状的墙**从内部是看不见的**
> - 翻转面法线以创造一个**相机能看到内部的中空空间**
> - 翻转选定的面以创造变化，例如**一个开顶的房间」**

★ **这是个会浪费几小时的 Unity 陷阱**：
ProBuilder 默认做出的房间是**实心的**，墙从内部看不见。
做室内必须翻面法线。

### 该测量的尺寸（来自一份整理良好的灰盒指南）

门高度 / 走廊宽度 / 台阶高度 / **平台间隙** / 掩体尺寸 / 目标可见性

★ 首次 blockout **不要**做的：建模最终道具、装饰、倒角、贴花、
复杂纹理、精细光照。

## 《进击的巨人》房屋尺寸：❌ 未找到

明确结论：
- 无官方设定集、无模型公开数据
- 现有素材全是民间重建，且作者自己承认改动了比例
  （FoxicalOW 的 Minecraft 重建把城墙从 50 格加高到 100 格，
  「以保证房子能超过 8 格高」—— 说明原作民居在方块尺度下不够高，
  他是靠改城墙解决的）
- 唯一公开的程序化住宅方案（Brian Valentin-Ranc，Houdini，
  ArtStation）也没有公布尺寸数字

**建议**：不要等AOT 数据，直接用真实日本住宅法定尺寸做 ——
AOT 的日本性本来就来自真实日本住宅。
