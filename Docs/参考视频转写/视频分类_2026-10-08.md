# 视频资料分类 —— 按「与本项目的可迁移性」

> 调研日期：2026-10-08
> 项目：**zhizhu**（Unity 2022.3.62f3c1，Z-up 坐标系，球体玩家 + 蛛丝摆荡）

## ★ 分类标准：不是按「视频质量」，而是按「能不能用在我们项目里」

本项目是 **Unity 2022.3LTS**，所以判断标准是：

| 类别 | 判据 | 处理方式 |
|---|---|---|
| **A 直接可用** | 原理与引擎无关，Unity 有对应实现 | 值得深挖 |
| **B 原理可借鉴** | UE5/Godot 专有，但算法/思路通用 | 看原理，不抄代码 |
| **C 项目无关** | 我们的项目用不上 | 存档，不投入时间 |

★ **UE5 的一堆视频不等于我们能用** —— 但 UE5 的**动画算法**（FABRIK、
程序化 IK）与引擎无关，值得看。反过来 Godot 的 CSG 在 Unity 里没有对应，
但「用 CSG 做白盒」的思路可以借鉴。

## 一、逐个分类

### A 类：直接可用（3 个）

#### 1★ 八足蜘蛛程序化行走（`ULvaK9v`，11分16秒，虚幻仙贝）

**关联度：★★★**（八足蜘蛛 + 程序化动画，与我们的蜘蛛主题高度重合）

已转写核实，核心机制：

| 要素 | 内容 |
|---|---|
| 算法 | **FABRIK**（`Locomotor` 节点，UE5 的实验性插件）|
| 原理 | 「动态计算每条腿在角色移动时**因踩下的位置**，而不是依赖传统动画片段」|
| 骨架 | 蜘蛛 FBX → 创建 **FABRIK 节点** → 给每条腿加 `Target Control` 控制点 |
| 碰撞 | 每条腿末端挂碰撞体，射线检测落点 |
| ★ 关键调参 | 碰撞半径要很小（0.5）；最大碰撞高度 30 → 改到 **1~1.5** |

**★ 为什么对我们有用**：
⚠️ **修正我最初的判断**：核对项目后发现，球的形态是
`CreatePrimitive(PrimitiveType.Sphere)`（`SilkBuilder.cs:4492`）
——**纯球体，没有骨架、没有腿**。所以「八足蜘蛛」对我们**当下没有直接用途**。

它的真正价值有两点：
1. **印证了我们刚做的设计决策**：视频里同样是
   **碰撞半径远小于视觉半径**（碰撞 0.5 vs 身体更大），
   这与我们「视觉 1.25 / 碰撞 1.25」以及此前「视觉 4.5 / 碰撞 2.0」
   的分离思路一致 —— 有了第三方印证。
2. **若将来给球加腿**（项目主题是蜘蛛侠），这套
   「射线检测落点 + FABRIK 求解」就是标准做法。

**可迁移到 Unity**：FABRIK 可用 Animation Rigging 包或自己实现，
射线检测完全一致。**但前提是项目先有骨架**，目前没有。

#### 2. Godot CSG 关卡白盒（`jWDeTqg`，1分22秒，__zhan__）

**关联度：★★★**（正是我们在 `HouseBlockout` 手做的事）

已抽帧核实：画面是用原生 CSG 搭出的房间白盒，有门洞、可试玩、能测量尺寸。

**★ 对我们的价值**：
我们现在用 `Slab()` / `Wall()` **手搓薄板**（因为 Unity 的 ProBuilder
默认实心，从外面看不到里面）。CSG 路线是另一种解法：
**用布尔运算直接挖出门洞**，不用手工拼墙垛+ 门楣。

★ 但注意：Unity **没有内置 CSG**，ProBuilder 的 CSG 模式需要 ProBuilder 包
（我们项目当前没装，见 `Packages/manifest.json`）。
→ 结论：**思路可借鉴，工具不适用**。我们继续手搓薄板。

★ 顺带印证了我们 `HouseBlockout` 的一个现状问题：
`BuildDoorways()` 目前**只做了门楣，没做左右墙垛**，
所以门洞其实还没真正挖通。这个视频展示了「挖通后试玩」的目标状态。

#### 3. 投射物特效拆解（`doMzdLS`，13分19秒，虚幻仙贝）

**关联度：★★**（我们的蛛丝就是「投射物」）

标题即内容：头部、拖尾、支撑、运动与撞击的拆解。
**这是蛛丝视觉表现的直接参考** —— 我们现在只有`LineRenderer` 画一条白线。

值得看的点：丝线命中时的「支撑」表现、拖尾的宽度衰减、撞击的粒子。
★ 这能解决我们「丝线看起来太简陋」的问题。

### B 类：原理可借鉴（3 个）

#### 4. 肌肉晃动 / 次级运动（`cqs26kY`，11分39秒）

**关联度：★★**（生物感）
原理通用（惯性滞后、阻尼跟随），任何引擎都能实现。
★ 对我们的价值：球体若要「有生命感」，次级运动是低成本高回报的加分项。

#### 5. Transformer 动画系统（`KqXR6MQ`，52秒，VR控）

**关联度：★**（纯研究前沿）
⚠️ **实测发现：音轨 mean_volume = −48.9 dB，接近静音**
→ 是B站自动字幕音轨，**无解说**。只有片头「字幕by索兰娅」。
→ 若要看内容必须抽帧读字幕，52 秒的信息量有限。
**结论：暂缓**，除非我们需要MLP/Transformer 动画方案。

#### 6. Control Rig Physics 骑马次级运动（`fGMJMae`，44分58秒）

**关联度：★★**
UE5 专有（Control Rig 是 UE 的动画系统），但「次级运动」的解法通用。
★ 与第 4 个重叠，可只看第 4 个。

## 二、结论：值得投入时间的是 3 个

| 优先级 | 视频 | 状态 |
|---|---|---|
| **1** | 八足蜘蛛程序化行走 | ✅ 已转写，机制已提取。**但对应当前项目无直接用途**（球无骨架）|
| **2** | 投射物特效拆解 | ⏳ **建议下一步转写** —— 直接改善蛛丝观感 |
| **3** | Godot CSG 白盒 | ✅ 已抽帧。结论：思路借鉴、工具不适用|

其余 7 个暂不投入时间。

### ★ 核对项目后的修正（重要）

我最初以为「八足蜘蛛」关联度最高，核对代码后发现**判断错了**：

```
SilkBuilder.cs:4492  var body = GameObject.CreatePrimitive(PrimitiveType.Sphere);
```

我们的球是**纯球体，没有骨架、没有腿**，所以八足蜘蛛这套程序化行走
**当下用不上**。它的价值降级为「印证我们的碰撞/视觉分离设计」+
「将来若加腿时的实现参考」。

★ 这正是本项目的教训：**不要因为标题看起来相关就高估价值，
必须核对代码确认现状。**

### ★ 顺带发现的现状问题

`HouseBlockout.BuildDoorways()` 目前**只做了门楣，没做左右墙垛**：
```csharp
Slab(tag + "_门楣", ...)   // 只有门楣，没有墙垛
```
→ 门洞其实**还没真正挖通**，球现在靠墙体碰撞是撞不开门的。
（虽然刚恢复的国标门洞 0.70~0.90 米对2.5 格的球很宽松，
但视觉上门洞是「贴了块门楣的整面墙」。）

★ 这是用户明确要求的「两层四间住宅」里**还没做完的部分**。

---

## 三、★ 重要提醒：这些都不能直接抄

本项目是 **Unity**，以下内容需要**在Unity 里重新实现**：

| 视频里的 | 在 Unity 里对应什么 | 工作量 |
|---|---|---|
| UE5 Locomotor（FABRIK）| Animation Rigging 包，或自己写 FABRIK | 中|
| UE5 Control Rig | Animation Rigging 包 | 中 |
| Godot CSG | ★ 无对应（ProBuilder 需装包）| — |
| 特效节点 | Particle System / VFX Graph | 中 |

★ **不要因为视频讲得清楚就以为能直接用**。这是本项目反复踩过的坑
（历史上曾因「参考访谈」而误判设定，用户明确要求「不要根据访谈和演示
视频猜人家的设定，要逆向解码」）。
