## 一、metapika/unity-procedural-animation（视频 1：Locomotor 之外新增）

**为什么有价值**：唯一一个把「步态参数」写成**带推荐数值清单**的 Unity 实现。
作者明确写「You can use any of this project's scripts」。

地址：`https://github.com/metapika/unity-procedural-animation`
Unity 2020.3.10f1，依赖 Animation Rigging + FastIK。

### 作者的参数经验值（原文）

| 参数 | 作者建议 | 含义 |
|---|---|---|
| Speed | 15 | 「够快的敌人，但动作又不明显」的速度平衡点 |
| Lerp Target | 速度 < 7 → **1.0**；速度 ≥ 7 → **1.1** | IK 目标插值的 lerp 系数随速度微调 |
| Step Distance | 需实测 | 触发迈步的距离 |
| **Overhead Amount** | **必须 < Step Distance**，建议 `StepDistance − 0.15`（快腿）/ `− 0.5`（慢腿） | ★ 见下 |
| Step Height | — | 抬腿弧线高度 |

### ★★ 核心机制：Overhead ≥ Step Distance 会导致无限前后反复

作者原话：

> "Overhead Amount - DO NOT set it higher than or equal to the Step Distance.
> If you do, the leg will move forward and backwards endlessly."

**这对应我们的 bug：「移动两步就需要重来」。**

在 `SilkSpiderBody` 里的准确形式（三段式换点的第三段缺失）：

```
start      = 当前落点（投影到水平面）
overshoot  = start + (站位 − start) × overshootMultiplier
projected  = overshoot + predictVel← ★ 这里没有任何夹紧
落点        = TraceGroundMulti(projected, ...)
```

**数值推导（本项目实测，非估计）**

设 `dev` = 当前落点到站位的偏差，`over` = 过冲倍数（1.5），
`pv` = predictVel 长度。则下一步偏差：

```
dev' = dev × (2 − over) + pv = 0.5 × dev + pv
```

这是个**线性递推**，平衡点（稳态偏差）：

```
dev_∞ = pv / (1 − 0.5) = 2 × pv
```

实测：`maxPredictLength = 3 × 半径`，predictVel 拉满时
`pv = 1.5`（半径取 0.5）→ **dev_∞ = 3.0**
而触发距离 `farLimit = 0.7 × 腿长 = 0.7`

```
dev_∞ (3.0) > farLimit (0.7)
→ 落点永远在触发区外 → 每帧都触发迈步 → 永不停止
```

**这就是「移动两步就重来」的确切机制。**

### ★ 我第一版修错了（数值模拟否掉的）

我最初以为机制是「偏差衰减太慢」，于是去**夹过冲量**。模拟直接否定：

|方案 | 偏差递推 | 收敛步数（dev₀=70） |
|---|---|---|
| 不夹 | `0.5×dev` 几何衰减 | **9 步** |
| 夹过冲量（错） | 固定步长线性递减 | **200+ 步** |

→ **夹过冲量让收敛慢了 20 倍，方向完全相反。**

正确做法：夹**最终偏差**。

```csharp
Vector3 devVec = defaultWorld − projected;
float devLen = devVec.magnitude;
float devCap = farLimit * maxDeviationRatio;   // 0.7
if (devLen > devCap)
    projected = defaultWorld − (devVec / devLen) * devCap;
```

夹后偏差 = 0.49 < farLimit 0.7 → **一步收敛，零振荡**。

### 过冲倍数的安全边界

`overshootMultiplier ≤ 2.0` → `travel ≤ dev` → 落点永不越过站位。
实测：

| overshoot | 落点 | 符号 |
|---|---|---|
| 1.5 | +0.500 | + |
| 2.0 | +0.000 | 0 |
| 2.5 | −0.500 | **− 越过站点** |
| 3.0 | −1.000 | **− 越过站点** |

我们的 `Range(1f, 2f)` 恰好安全（这是既有代码，运气好）。
**真正的越界来源是 predictVel**，已由偏差夹紧兜住。

### 验证脚本

`check_gait_convergence.py` —— 数值模拟 + 反向用例。
它同时测「夹紧开/关」两组，并自证 `overshoot > 2` 才越站位。

## 二、Arachnid-dev（jettelly 报道）

**为什么有价值**：Unity 3D，完整实现了「地面 + 墙面 + 天花板 + 转角」，
且**明确说明「相邻腿不同时迈步」**这条规则。

- 每条腿是**带旋转限制的关节链**
- 环境判定用**双向 SphereCast**：一个向下找地、一个向前找墙
- 附着靠**假重力对齐表面法线**
- 迈步触发：身体走太远导致腿**够不到**目标 → 理解为「该迈步了」
- 新落点：从该腿的**基础位置**出发，按移动方向前推一点，再多方向射线找有效面
- **身体稳定**：
  ```csharp
  float avgHeight = Average(legTargets);      // 高度 = 各落点均值
  Vector3 normal  = ComputeNormal(legTargets);// 法线 = 各落点拟合
  body.position.y = SmoothDamp(body.position.y, avgHeight);
  body.rotation  = AlignTo(normal);
  ```

→ 我们已有 `feetAvg` + `UpdateBodyPosture`，方向一致。

原文出处：`https://jettelly.com/blog/how-did-this-developer-make-a-procedural-spider-walk-in-unity`

## 三、dacaffee（Godot 4.5，80.lv 报道）

**为什么有价值**：证明「Marker 当 IK 目标、脚本只搬Marker」这个架构
在我们身上同样成立（我们的 `LockedTarget` 就是 Marker 的角色）。

要点：
- 未来位置 = 射线命中点 **+ 玩家速度**
- 距离超过阈值 → 触发step，用**弧线**把 IK 目标移到该点
- 腿**按对角配对分组**，同组只能有一组动
- 底盘高度 = 4条腿位置的均值
- 旋转 = 用 IK 目标位置拟合地形法线，对齐 body
- ★ **悬停效果**：正弦波轻微改变高度

→ 与我们的交替四足步态同源。**「正弦悬停」我们还没做**，
  是唯一可直接搬过来的新增项（身体轻微起伏）。

出处：`https://80.lv/articles/ik-driven-procedural-spider-locomotion-in-godot-4-5`

## 四、线控陷阱（UE5 Control Rig，80.lv）

**为什么有价值**：作者记录了一个用**血泪**换来的结论，正好对应我们的实现。

> "I had one issue where the legs of the spider were touching the ground
> and everything was working, but sometimes they were intersecting with
> objects, for example, when going up a ramp and then getting down...
> After a while of pulling out hair, I realized that I was line tracing
> straight above the leg joint."

**教训**：落点射线必须**从腿关节正上方打**，不能从身体中心或脚当前位置打。
否则坡道上下坡时，腿会插进坡体。

→ 我们的 `TraceGroundMulti` 从 `projected` 起点打，
  需确认 `projected` 的水平位置与站位一致。**这条待实机验证。**

另外：
- 速度用 `Velocity = Distance / Time` 算，再乘到锁定点上
- 每条腿**独立计时**，各自错开
- 抬腿用**曲线**（我们用 sin，等价）
- 骨盆用 **spring interpolation** → 有弹性起伏

出处：`https://80.lv/articles/how-to-set-up-procedural-turret-animation-with-unreal-engine-s-control-rig`

## 五、Codeer「Unity procedural animation tutorial (10 steps)」★ 视频 2

**为什么算「有实际帮助」**：这是 Unity 官方 Learn 页与HangyBoi 的portfolio

时间轴（README 原文）：

| 时间 | 内容 |
|---|---|
| 0:58 | Step 1 给腿建 IK |
| 6:27 | Step 2 把腿固定到地面 |
| 9:52 | Step 3 给身体加距离检测器 |
| 12:11 | Step 4 向下射线确认检测器着地 |

### ★★ 作者的默认数值（可直接对照）

```csharp
public float legMoveSpeed        = 7f;   // 插值速度
public float moveDistance        = 0.7f;  // 触发距离
public float moveStoppingDistance = 0.4f;  // 停止距离
```

**★ 关键数值关系：`moveStoppingDistance / moveDistance = 0.4/0.7 ≈ 0.571`**

> 这与我们上一轮推导的收敛条件 `maxDeviationRatio < 1.0` 是**同一件事**：
> 作者用「停止距离 / 触发距离 < 1」保证腿不会冲过头。
> 他用两个独立参数，我们用「过冲 + 夹紧」，殊途同归。
> **我们默认值 0.7 与他的 0.7 完全一致** —— 这是一个独立的第三方交叉验证。

### ★★ 我们没有的机制：对侧腿互斥（oppositeLeg）

作者的判据（原文）：

```csharp
if ((distanceToMoveCube >= moveDistance && !oppsiteLeg.isItMoving()) || moving)
```

**相邻/对侧腿互斥**：一条腿在摆动时，对侧腿**不允许**开始摆动。
靠一个 bool `isMoving` 互相通知。

→ **我们有相位约束（交替四足步态保证同相腿不会同时摆动），
  但没有「空间上相邻的腿」互斥。**
交替四足只保证 L1/L3 同时、R1/R3 同时，但**没有额外禁止 L1 与 L2 摆动重叠**。
Arachnid-dev 也写了同样一条规则（"Nearby legs do not step at the same time"）。
→ **两个独立来源都提到这条，值得落地。**

### ★ 作者的「抬腿」实现方式与我们不同

```csharp
// 移动时：往 cube + 0.3 走
transform.position = Lerp(pos, cube.position + (0,0.3,0), dt*speed);
// 站立时：往 originalPosition + (0,-0.3,0) 走  ← 压进地面
transform.position = Lerp(pos, originalPosition + (0,-0.3,0), dt*speed*3);
```

★ 注意：作者**不用显式的抬腿弧线**，而是「站立时往下压 0.3」制造离地感。
我们用 `sin` 弧线（dacaffee / UE5 教程的做法）。
→ 两种做法都可以，但作者的版本代码量小得多，值得对照我们的是：
  **他明确区分了「移动中插值速度」与「站立回位插值速度」两个值**
  （`legMoveSpeed` vs `legMoveSpeed * 3f`）。我们目前只有一个 lift 概念。

出处：`https://github.com/parisyup/ProceduralAnimationForTheKiwiCoder`
